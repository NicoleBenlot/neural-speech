Build a complete Python project named neural-speech.

The goal is to create an experimental custom neural speech system, initially focused on STT (speech-to-text), with the architecture prepared for TTS (text-to-speech) later.

The project must support incremental/continued training. A trained model must be saved as a versioned checkpoint and later reused as the starting point for additional training on new datasets while retaining previously learned knowledge.

Do not use a pretrained STT/TTS model as the core neural model. This project is intended to train an original experimental model from the user's own speech dataset.

1. Current dataset

The existing raw dataset has this structure:

data/
└── raw/
    ├── index.txt
    └── assets/
        ├── 1.opus
        ├── 2.opus
        ├── 3.opus
        └── ...


The index.txt is grouped by prefixes and maps words to numeric audio IDs.

Example:

[ad]
adlaw = 104
adto = 83

[ak]
ako = 24
akoa = 41
akong = 35

[am]
amo = 44
among = 38

[an]
ang = 1
anhi = 84


This means:

104.opus → "adlaw"
83.opus  → "adto"
24.opus  → "ako"
41.opus  → "akoa"
35.opus  → "akong"


The [ad], [ak], etc. sections are organizational metadata only and must not be treated as neural-network classes.

The numeric ID identifies the audio file.

The actual training relationship is:

audio → transcription


The current recordings are primarily isolated word recordings.

Do not assume that the current dataset contains complete sentences.

2. Dataset parser

Create a parser for the existing index.txt format.

The parser must:

Ignore blank lines.
Detect section headers such as [ad].
Parse entries in the form word = integer.
Preserve the exact word transcription.
Extract the integer audio ID.
Resolve the audio path as:
data/raw/assets/<id>.opus


For example:

adlaw = 104


becomes:

{
    "id": 104,
    "audio_path": "data/raw/assets/104.opus",
    "text": "adlaw"
}


The section name should be preserved as optional metadata but must not be required by the model.

Do not modify the original index.txt.

3. Processed manifest

Create a preprocessing command that converts the raw index into a normalized manifest.

Example:

data/
├── raw/
│   ├── index.txt
│   └── assets/
│
└── processed/
    └── manifest.csv


Example manifest:

id,audio,text,section
104,data/raw/assets/104.opus,adlaw,ad
83,data/raw/assets/83.opus,adto,ad
24,data/raw/assets/24.opus,ako,ak
41,data/raw/assets/41.opus,akoa,ak


The manifest is an intermediate representation and should make the PyTorch dataset independent from the unusual original index format.

5. Audio preprocessing

Internally convert all audio into a consistent representation.

Default:

Sample rate: 16000 Hz
Channels:    mono
Format:      float32 tensor


The preprocessing pipeline should:

Load .opus.
Decode compressed audio.
Convert to mono.
Resample to 16 kHz.
Convert to a PyTorch tensor.
Perform safe amplitude normalization if appropriate.
Return the waveform and sample rate.

Do not feed Opus compression directly into the neural network.

Make audio preprocessing reusable by both training and inference.

6. Text/token system

Implement a configurable tokenizer/vocabulary.

Initially support character-level tokenization.

Example:

"adlaw"


becomes something equivalent to:

[a, d, l, a, w]


Include special tokens:

<PAD>
<UNK>
<BOS>
<EOS>


Do not use the numeric audio ID as the target class.

The model should learn text sequences, not the arbitrary dataset IDs.

Save the vocabulary with every model version.

For future expansion, the tokenizer should be replaceable with a subword tokenizer without rewriting the model or dataset architecture.

Implement a custom collate_fn that supports variable-length audio and text sequences.

Use appropriate padding and padding masks.

11. Versioned checkpoints

This is a core requirement.

Never overwrite the previous trained model.

Use:

checkpoints/
├── v001/
├── v002/
├── v003/
└── latest.json


Each version should contain:

checkpoints/v001/
├── model.pt
├── optimizer.pt
├── scheduler.pt
├── vocabulary.json
├── config.json
├── training_state.json
└── manifest.json


training_state.json should contain information such as:

{
  "version": 1,
  "epoch": 10,
  "global_step": 5000,
  "dataset_version": "v001",
  "parent_checkpoint": null,
  "train_loss": 0.0,
  "validation_loss": 0.0,
  "wer": 0.0,
  "cer": 0.0
}


Do not use fake metric values in actual execution; the example above is only structural.

12. Resume training

13. Incremental training

Support training with new data:

python -m src.training.train \
    --from-checkpoint checkpoints/v001 \
    --dataset data/processed/manifest_v002.csv


The model must initialize from v001 and produce a new version:

v001
 ↓
new dataset
 ↓
v002


Never destroy v001.

14. Replay / catastrophic forgetting prevention

Implement optional replay training.

When training on new data, allow a configurable percentage of samples from previous datasets to be mixed into the new training set.

Example:

python -m src.training.train \
    --from-checkpoint checkpoints/v001 \
    --dataset data/processed/manifest_v002.csv \
    --replay-manifest data/processed/manifest_v001.csv \
    --replay-ratio 0.30


Meaning:

70% new data
30% replay data


The implementation should make the replay ratio configurable.

The purpose is to reduce catastrophic forgetting.

Do not claim that replay completely prevents forgetting.

15. Regression evaluation

When incremental training is used, evaluate both:

new dataset
old/reference dataset


This is important.

For example:

Before v002:
old WER = 12%

After v002:
old WER = 14%
new WER = 8%


This allows us to see whether learning new data damaged previous capabilities.

Store these metrics in the checkpoint metadata.

29. Important conceptual rules

The implementation must follow these rules:

Rule 1

The numeric audio ID is an identifier, not a class label.

Rule 2

The model learns:

audio → text


not:

audio → numeric ID

Rule 3

The original index.txt is immutable source data.

Rule 4

Processed manifests are derived data.

Rule 5

Checkpoints are immutable versions.

Rule 6

New training starts from an existing checkpoint when requested.

Rule 7

Old checkpoints must never be silently overwritten.

Rule 8

Incremental training should support replay data to reduce catastrophic forgetting.

Rule 9

Every new model version should be evaluated against both new and previous/reference data where possible.

Rule 10

FastAPI is an inference layer, not a training layer.

Rule 11

The system must work with the current isolated-word dataset while remaining compatible with future sentence-level recordings.
